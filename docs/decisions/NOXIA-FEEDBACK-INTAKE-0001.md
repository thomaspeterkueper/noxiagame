# NOXIA Feedback Intake 0001 — authenticated persistence contract (draft)

Status: proposed; **not deployed**. A versioned, **unapplied** schema migration now exists at `supabase/migrations/20261031080000_player_feedback_submissions.sql`. Scope: direct player feedback and explicitly submitted NPC-conversation proposals.

## Verified prerequisite (2026-10-31)
Read-only inspection of the public Supabase schema found **no** table whose name contains `feedback` or `proposal`. Therefore the draft UI must never claim successful submission without a validated server receipt; the migration remains unapplied. No production schema change is authorized by this document.

## Submission contract
- POST `/api/game/feedback` requires a valid server-verified Supabase user, body validated with `validateFeedback`, bounded request size, and server-enforced rate limiting. The feedback object has an explicit field allowlist: unknown client metadata (including claimed votes, ownership, approvals or Core actions) is rejected rather than silently accepted. This is defense in depth; the server still never grants civic or world authority.
- For direct feedback, source kind `direct`. For conversation feedback, the server first validates the full feedback payload and public-receipt privacy contract without a database query; only then does it resolve `npc_conversation_log:<id>` against the authenticated player's identity with a read-only, owner-scoped lookup. Invalid drafts cannot spend a service-role ownership query. Never trust client-supplied `ownerVerified`; successful validation alone confers no ownership or civic authority.
- Require an idempotency key bound to owner and payload. Generate UUID, owner ID, creation time, and initial `submitted_for_review` status server-side. Reject duplicate/conflicting keys deterministically.
- Store private provenance separately from any publishable text. Client location hints are **unverified**. Public visibility requires explicit consent and human moderation; consent is not publication.
- GET `/api/game/feedback` lists only the authenticated owner's submissions and statuses. Never expose private NPC transcripts or another player's submissions.
- No feedback endpoint can emit Core events, alter parcels, grant ownership, approve civic initiatives, or execute engineering tasks.

## Read-only receipt endpoint (staged, not deployed)
A GET-only endpoint now exists at `app/api/game/feedback/route.ts`. It requires a verified Bearer JWT and uses a fresh Supabase client with the **anon key plus caller JWT**, never the service-role client, to select only `id,title,status,created_at`. Owner isolation is enforced by the staged table's `auth.uid()` RLS policy; the caller does not receive SELECT privilege on `owner_user_id`, so the query must not filter on that private column. Results are limited to 1–50, projected through the private-field-stripping receipt contract and returned with `Cache-Control: private, no-store`. Invalid limits return 400, unauthenticated calls 401, missing schema or database errors 503; the route does not insert or mutate world state. The CI guard for this route is **static** and cannot prove runtime JWT isolation. Before release: execute the migration in an isolated environment, test two distinct authenticated accounts, verify the full Next.js build, and then separately authorize deployment. A separate **direct-only POST** handler and an explicit form submission action are staged; they are not deployed and cannot store feedback until the migration is separately approved and applied.

## Private player receipt panel (staged, not deployed)
The `/earth/feedback` page now mounts a read-only **Meine Vorschläge** panel alongside the existing local-only draft form. On explicit user action, it retrieves the current session bearer token, calls `GET /api/game/feedback?limit=20` without caching, and validates the owner-only/review-only response envelope before displaying a bounded list of receipt titles, dates and review statuses. It never forwards private provenance or exposes an API write action. It handles signed-out, empty and unavailable states separately and cancels in-flight reads when collapsed. The panel does **not** imply that submissions exist: the migration remains unapplied. The POST handler and explicit form submission action are staged only. The panel wiring check is static; browser and two-user RLS integration tests are required before release.

## Review status contract (implemented as pure logic, not yet persisted)
The status lifecycle in `lib/game/evolution/feedbackReviewStatus.ts` is `submitted_for_review` → `under_review` → `needs_information` / `accepted_for_planning` / `declined` / `closed`. `needs_information` can return to `under_review`; `accepted_for_planning` can close. `declined` and `closed` are terminal. Status transitions are **not** permission checks: only an authenticated, audited moderation service may write status changes. Even `accepted_for_planning` is neither a civic approval nor permission to change the world. Unknown status values fail closed.

## Required persistence and security review
Proposed relation `player_feedback_submissions`: `id uuid`, `owner_user_id uuid`, `category`, `title`, `description`, `location_hint`, `requested_visibility`, `publication_consent`, `source_kind`, `private_source_ref`, `status`, `created_at`, `updated_at`, `idempotency_key`, `payload_fingerprint`. The staged migration binds `owner_user_id` to the verified Supabase Auth UUID (`auth.uid()`), not to a client-supplied profile ID. It enforces field lengths/check constraints, uniqueness `(owner_user_id,idempotency_key)` and an owner/creation-time index.

RLS is enabled in the staged migration. Authenticated clients get **SELECT on receipt columns only** (`id`, `title`, `status`, `created_at`), with an owner-only RLS policy; anonymous clients have no grants. INSERT/UPDATE/DELETE are **service-role only**, never direct client writes, so clients cannot spoof owner, provenance or status. Service-side moderation still needs separate, audited authorization and transition enforcement. Verify Data API grants independently of RLS. The staged migration now includes a SECURITY DEFINER trigger with an owner-scoped transaction advisory lock and a rolling cap of **five new submissions per hour**, plus idempotency-key retry handling. This has **not** been executed against PostgreSQL. Retention policy, privacy review, and server-side moderation remain required before live intake. A read-only metadata test exists at `supabase/tests/player_feedback_submissions.test.sql`; the CI smoke check at `scripts/test-player-feedback-migration.cjs` checks text invariants only and does **not** execute SQL or prove JWT/RLS isolation.

## Two-user RLS integration harness (staged, NOT executed)
`scripts/test-player-feedback-rls-local.cjs` provides a disposable **local-only** Supabase integration test. It refuses non-HTTP/non-loopback endpoints, requires the explicit `NOXIA_FEEDBACK_RLS_TEST=local-disposable` opt-in and distinct local anon/service keys, and never touches Core/world tables. After the reviewed migration is applied to a throwaway local Supabase instance, run it with `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` pointing **only to that local instance**. The harness creates two temporary confirmed Auth users and one receipt per user; it checks own-row visibility, cross-user invisibility (including a targeted foreign-ID lookup), anonymous denial, private-column denial, and refusal of direct client writes/status changes. It deletes fixture rows and users in `finally`; cleanup failures mark the run failed. The harness also exercises the **atomic per-owner rate trigger** with five concurrent insert attempts after one existing row (expect four accepted, one `P0001` rejection), checks the five-row cap, duplicate-key `23505` behavior for identical and conflicting payloads, and confirms that a different owner's inserts are unaffected. These checks require a disposable local database; they are **not executed by CI**. Additional defense in depth: `scripts/feedback-local-only-fetch.cjs` is supplied to **every** Supabase client in the disposable harness. It permits only the originally approved loopback HTTP origin and forces `redirect: 'manual'`, rejecting HTTP 3xx responses instead of following a redirect to another server. `scripts/test-feedback-local-only-fetch.cjs` verifies origin, port, credentials and redirect rejection with a fake transport and **no network**; CI executes it. This guard cannot prove that a process listening on loopback is not itself a forwarding proxy, so the operator must still use an isolated throwaway instance. The database uniqueness errors are not an executed test of the HTTP API's replay/409 mapping. It does **not** test the HTTP POST route, real production grants, or the full browser flow. CI runs `node --check` on this script and `scripts/test-player-feedback-rls-safety.cjs` as a negative-only process test. The latter verifies that missing opt-in, remote URLs, URL credentials and absent/identical keys are rejected **before any database connection**. These are safety-gate regressions, not SQL/RLS execution: **no live RLS or concurrent-rate integration test has yet passed**. Keep the migration and deployment separately gated.


The pure feedback submission gate now also rejects syntactically valid 19-digit NPC receipt IDs that exceed PostgreSQL's signed `bigint` maximum (`9223372036854775807`), matching the server-side ownership gate. Boundary regression cases are included in the contract tests; this is not an executed database test.

## Authenticated NPC conversation source gate (staged, 2026-10-31)
The POST handler now uses `parseAuthenticatedFeedbackPost`: direct submissions retain their previous fingerprint; conversation submissions accept **only** `{kind:'conversation',sourceRef:'npc_conversation_log:<id>'}`, never client-supplied `ownerVerified`. A service-role **read-only** lookup restricts `npc_conversation_log.id` and `player_profile_id` to the authenticated Supabase Auth user UUID (the log's foreign key references `auth.users(id)`). Only `id,player_profile_id` are read. Missing, foreign and failed lookups return the same 422 error. The normalized private source reference is stored separately from publishable fields and included in the idempotency fingerprint. Every submission remains `submitted_for_review`; no civic/Core/world action follows. The new parser has mocked-owner tests and a static route boundary check, but **no two-user HTTP/SQL integration test has passed**. This is a staged code change only; do not deploy or apply the migration until isolated RLS, route, build and privacy review are complete.

## Read-only NPC conversation source ownership gate (staged; connected to draft POST)
`lib/game/evolution/conversationSourceOwnership.server.ts` now defines a fail-closed, server-side **read-only** check for `npc_conversation_log:<bigint-id>` receipts. The caller must supply the authenticated Supabase Auth UUID, not a client-provided owner. Its injected database reader selects **only** `id,player_profile_id` and filters on **both** log ID and verified owner ID. Foreign, absent and failed lookups return the same `conversation_source_unavailable` result; malformed references are rejected before querying. Unsafe JavaScript numeric bigint decoding fails closed; valid bigint strings remain supported. No transcript text is read or returned. Pure mocked-query regression tests run in the feedback CI. **The draft POST route now invokes this gate for conversation submissions** after local payload validation. The real database, RLS, JWT, privacy and HTTP integration tests have not been executed. A reviewed service-role adapter and explicit end-to-end tests remain release prerequisites; a successful ownership lookup grants neither publication nor civic/Core authority.
